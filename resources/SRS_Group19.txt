1. Introduction
1.1 Purpose
This document specifies the software requirements for the Rail and Road-based Supply
Chain Distribution System (SCDS) being developed for Kandypack, an FMCG
manufacturer based in Kandy, Sri Lanka. It describes the functional and non-functional
requirements, the data model and the business rules that the system must follow. This document
serves as a guide for the design, implementation, testing and maintenance of the SCDS.

1.4 Product Scope
The system replaces Kandypack’s existing Excel-based logistics tracking process with a
centralized, database-driven platform that:
● Automates train cargo capacity scheduling, including transferring excess orders to the
next available trips.
● Manages last-mile truck deliveries based on predefined routes.
● Schedules drivers and assistants while ensuring compliance with working-hour limits
and assignment rules.
● Tracks orders and delivery statuses throughout the complete delivery process.
● Generates operational and sales reports to support management decisions.

2. Overall Description
2.1 Product Perspective
The SCDS is a new, self-contained system developed to replace Kandypack’s existing Excelbased logistics tracking process. It:
● Replaces spreadsheets used for managing orders, delivery schedules and driver rosters.
● Automates logistics operations by enforcing capacity limits, scheduling rules, and
delivery status updates.
● Provides reporting features to support management decisions.
● May support future integration with external services such as mapping or notification
systems.

Order Management
● Allows customers to place orders containing multiple products with quantities and a
delivery address.
● Validates orders based on route coverage and the 7-day minimum advance-order

● Manages truck schedules while checking conflicts between trucks, drivers, and
assistants.
● Maintains driver and assistant rosters according to weekly working-hour limits (40

High priority.

4.1.3 Functional Requirements:
● The system shall reject an order whose delivery address does not map to an existing

● The system shall allow an order to contain one or more OrderItem rows, each

4.2 Train Scheduling
4.2.1 Description and Priority:
The system assigns order items to train trips by cargo capacity and product space consumption;
overflow moves to the next available trip. High priority.
10

Rail and Road-based Supply Chain Distribution System - Group 19

4.2.2 Stimulus/Response Sequence:

4.2.3 Functional Requirements:
● The system shall compute required space for each OrderItem as quantity ×
Product.unit_space_consumption.
● The system shall never allocate more than a TrainTrip’s max_capacity (enforced by a
database trigger, not application logic alone - see Section 5.5).
● Where a single OrderItem cannot fit entirely within one trip's remaining capacity, the
system shall split it across an OrderTrainAllocation row on the current trip and one or
more rows on subsequent trips, preserving total quantity.
● The system shall run allocation inside a single database transaction so that a failure
partway through never leaves an OrderItem partially, inconsistently allocated.

4.3.1 Description and Priority:
Order items arriving at a store are scheduled onto trucks for last-mile delivery; trucks, drivers
and assistants must not be double-booked. High priority.

5. Database Design Overview
Because this project's main deliverable is a database rather than an application, this section sets
out how the logical data model, the integrity rules and the reporting needs described earlier
translate into concrete database objects: tables, keys, procedures, functions, triggers and
indexes.

5.1 Design Principles
•

•

Every entity has a single-column primary key and every relationship is enforced with a
foreign key, so referential integrity is guaranteed by the database rather than by
application code alone.
An order can contain several products, so orders and order lines are modelled as two
separate tables (Order and OrderItem) rather than repeating order details on every line,
in line with normal form.

•

Rules that must never be broken - cargo capacity, double-booking and working-hour
limits - are enforced with triggers and stored procedures at the database level, so they
hold even if a bug in the application layer would otherwise allow a bad write.

•

Multi-step operations, such as placing an order with several lines or assigning a truck
trip and updating several order statuses at once, are wrapped in stored procedures so
they either fully succeed or fully roll back, preserving the database's atomicity and
consistency (two of the ACID properties).

5.4 Triggers

● A BEFORE INSERT/UPDATE trigger on OrderTrainAllocation that blocks any
allocation which would push a TrainTrip's total allocated space over its max_capacity.
● A BEFORE INSERT trigger on TruckTrip that blocks any truck, driver, or assistant
being booked for an overlapping time window.
● A BEFORE INSERT trigger on TruckTrip that calls calculate_weekly_hours() and
rejects the assignment if it would take the driver over 40 hours, or the assistant over 60
hours, in that week.
● A BEFORE INSERT trigger on TruckTrip that rejects a driver's third consecutive
delivery, and an assistant's third consecutive route, in line with the roster rules.
● An AFTER UPDATE trigger on Order that records a timestamped status-history row
whenever status changes, so delivery-performance reports have a full audit trail.
● An AFTER UPDATE trigger on DeliveryItem that checks whether all DeliveryItem
rows for the parent Order are now “Delivered” and if so updates Order.status to
“Delivered” automatically.

5.6 Test Data

To demonstrate the schema and its constraints, the delivered database is populated with a
realistic test dataset, in line with the project brief:
● At least 40 customer orders, spread across several months so quarterly reports have
meaningful data.
● At least 10 delivery routes, covering the six destination cities named in the brief.
● A full train schedule with defined capacities, sufficient to exercise the overflow-tonext-trip logic.
● Enough truck trips, drivers and assistants to exercise the double-booking and workinghour triggers, including at least one case per trigger that is expected to be rejected, to
prove the constraint works.

6. Other Nonfunctional Requirements
6.1 Performance Requirements
● Common user interactions (viewing orders, submitting a new order, viewing a
schedule) should return within 1-2 seconds under normal load - realistic for a round trip
that includes validation and a database write. A 100 ms target is not achievable for these

6.2 Security Requirements
● Access is controlled by username and password login, with passwords stored as salted
hashes rather than in plain text.
● Role-based access control ensures customers can only see and manage their own orders,
while staff see only the functions relevant to their role.
● After logging in, a user receives a session token (e.g. a JSON Web Token) valid for 24
hours, so they are not asked to log in again during that period.
● All database writes that affect scheduling or working hours go through the procedures
and triggers in Section 5, so the rules cannot be bypassed by direct data entry.

6.3 Software Quality Attributes
● Usability: interfaces for customers and staff should be simple enough to use with little
to no training.
● Availability: the production system should target 99% uptime, consistent with the
assumption in Section 2.7 that it runs on a persistent server.
● Maintainability: the data model and constraints are documented here and in the schema
itself, so the rules governing scheduling and rostering are easy to find and change if the
business rules change.
● Data integrity: enforced primarily at the database layer, so it holds regardless of which
part of the application writes the data.

6.4 Business Rules
● An order must be placed at least seven days before its requested delivery date.
● An order can only be accepted if its delivery address is covered by an existing route.
● A train trip cannot be loaded beyond its stated cargo capacity; any overflow moves
automatically to the next available trip.
● A truck, driver, or assistant cannot be booked for two overlapping trips.
● A driver must not be scheduled for two consecutive truck deliveries.
● An assistant must not be scheduled for more than two consecutive routes.
● A driver cannot work more than 40 hours in a week; an assistant cannot work more than
60 hours in a week.

7. Other Requirements
For now, only English is supported throughout the system. Support for other languages may be
added later.
